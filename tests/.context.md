Vitest tests. The rule engine, the theme logic, the sync settings, the GitHub client with its retry, the dashboard composable, and the embedded test config have tests. `npm test` runs them.

## Summary

- requiredFieldRules.test.ts — FIELD-001 and FIELD-002 with the real field names: each required field, `0`, `Yes`, `No`, and `N/A` as valid, per-field messages, optional and separator fields, the four not-evaluated states, Start with Status Todo, empty or unavailable Status, config names, disabled rule
- milestoneRules.test.ts — MILESTONE-001: empty milestone, the two allowed names (case and spaces ignored), other names with the current value, every category, names from the config, empty list, disabled rule
- githubProject.test.ts — value shapes seen in the real API (`null`, text, option, number), items related by `content.id`, pull requests and drafts ignored, invalid responses
- projectFields.test.ts — merge by `content.id` (item ID equal to another issue ID), outside the Project, not found, query error, no separator field, failure to field state
- githubProjectClient.test.ts — Project calls with a stubbed `fetch`: the `fields` parameter, pagination by `Link`, refusal of a foreign link, only issue items, one item, API version header, 401, 403, and 404 messages
- classifyIssue.test.ts — `classifyIssue` table: type match, spaces and case, unknown type, type over label, label fallback, both labels, no labels, blank type, names from config
- engine.test.ts — `evaluate` cases: rule findings, accepted regression title, unavailable field as not-evaluated, zero children not counted as complete; plus synced issues (stubbed `fetch`) that get task rules, not-evaluated checks, and no false errors; issues come from small factories in the file
- github.test.ts — `GitHubClient` with a stubbed `fetch`: 401, 403, and 404 messages without the token, empty repository, pull request filter, token only in the header, category and origin for each classification path
- githubRetry.test.ts — retry with a stubbed `fetch` and an injected wait: Retry-After, rate-limit reset, 5xx, retry and wait caps, no retry for 401 and 404, and `waitWithAbort`
- useAuditDashboard.test.ts — composable (also with a Project: values by issue, no access, query failure, no Project number, update by item ID) with a stubbed `fetch` and mocked config: sync status, missing token makes no fetch call, a second sync clears old rows, and the single-issue update
- filterIssues.test.ts — `matchesFilters` table: search, assignee, category, severity, view, and date field
- issueAuditState.test.ts — `getIssueAuditState` table: findings, findings with an unchecked rule, unchecked rule, category Outro, clean
- AppHeaderFooter.test.ts — header (name link, navigation links with the current page marked, connection text, Settings button, no connection details) and footer (text, "Sobre" link, repository link)
- SettingsPanel.test.ts — the panel (labeled closed dialog, connection values, token state without a value, failure reason, close button) and the compact connection line
- AboutView.test.ts — About page: real control names, the four cards, the numbered steps in order, no publisher detail (`.env`, token, permissions), no accordion, no real-time promise, result states, no internal rule code, contact states, way back
- developerInfo.test.ts — no invented contact, only `https:` and `mailto:` accepted
- useCurrentPage.test.ts — hash to page

- config.test.ts — the token and repository URL are empty strings under test

- useTheme.test.ts — theme resolution, saved-value check, blocked storage, and theme switch

## Guidance

- Tests SHOULD build synthetic issues inside the test file and clone them before changing them.
- Tests MUST NOT use a real token. `vite.config.ts` defines empty values in test mode.
