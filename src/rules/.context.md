Pure audit engine. `evaluate` takes issues and a config. It returns findings and not-evaluated checks. It does not touch Vue, the network, or storage. Each rule family lives in `validators/`.

## Summary

- engine.ts — `evaluate`: runs task or subtask rules per issue by its `category` (set by `services/classifyIssue.ts`), then milestone and field rules, then sibling feature-flag checks
- context.ts — shared helpers: `addFinding`, `addNonEvaluated`, field readers, and `getFieldAvailability` (not queried, no access, not found, or query failed)
- validators/ — rule families: task, subtask, field, and required-field rules (`requiredFieldRules.ts`: FIELD-001 required fields, one finding per empty field, and FIELD-002 Start when the Status is not Todo)

## Constraints

- A finding MUST come from a rule ID that exists in `services/config.ts`. `addFinding` drops any rule that is missing or disabled.

## Guidance

- A finding or a not-evaluated result MUST hold message keys and data (`MessageRef`), never a translated text. Field names from the Project stay as plain strings; an app-owned label (such as the title field) is a key.

- When a field is unavailable, a rule SHOULD call `addNonEvaluated`, not `addFinding`. The check then reads as "not checked", not "empty".
- Field names in the title and feature-flag rules (`Status`, `Tag`, `FF Name`, `FF Status`, `Initiative`) are literal strings. Required fields, the Start field, and the ignored separators come from `defaultConfig`. A rename in `fields` breaks a rule without a compile error.
- Rule code SHOULD stay free of Vue, network, and storage imports. The current files import only types and sibling rule modules.
